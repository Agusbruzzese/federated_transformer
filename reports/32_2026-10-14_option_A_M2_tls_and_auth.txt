1. WHAT M2 ADDS
  - TLS: every connection between the sites (SuperNodes) and the server
    (SuperLink) is encrypted and the server is authenticated by a
    certificate. A private test certificate authority (CA) signed the
    SuperLink certificate (SAN localhost, flserver, 127.0.0.1); the sites
    trust only that CA.
  - Site authentication: the SuperLink runs with --enable-supernode-auth.
    Each site has an ECDSA P-384 key pair. Only sites whose public key was
    registered by the operator ("flwr supernode register <key>") can
    connect.
  Flower 1.39 note: the static key-list option (--auth-list-public-keys)
  has been removed; keys are registered through the Flower CLI. The
  launcher does this automatically (--register-keys).

3. NOTE ON TRAFFIC IN THE CURRENT RUNTIME
  The loopback total (about 250 MB for 3 rounds) is about 4.8x the model
  payload (51.8 MB), because each update is relayed through several local
  hops (ClientApp -> SuperNode -> SuperLink -> ServerApp, and back). On
  real separate machines only the SuperNode <-> SuperLink hop crosses the
  network. That hop is the one TLS protects, and its size is about the
  payload. Measured precisely in the container/multi-machine tests.

4. VERDICT
  M2 PASSES. Encryption and site authentication are in place, they do not
  change the computation, and they reject unencrypted connections,
  untrusted certificate authorities and unregistered sites.

5. WHAT M2 DOES NOT DO
  - The test CA and keys are local test material. A deployment needs
    properly managed certificates (e.g. an organisation's CA) and key
    distribution.
  - TLS hides the traffic from the network, not from the server. The server
    still sees each site's individual update: that is M3 (secure
    aggregation).
