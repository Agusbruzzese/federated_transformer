1. PURPOSE
  Provide one simulator that can train every arm of protocol v2 on the
  frozen folds, under the protocol's data rules, and prove that it does
  what it claims before any real run is made.

2. WHAT WAS BUILT
  fedsim2.py is a NEW file. It is a copy of committee C's simulator after
  the B1 fix (C_federated/fedsim.py; that file is left as is), extended as
  follows:
  - Folds: --fold 0|1|2 reads folds.json (sha 79f3b1ff...). IID clients
    have the same sizes as the natural clients, with events assigned by a
    seeded permutation (seed 1000 + fold).
  - Arms:
      --arm central (C256, C64, and S+C with --init)
      --arm fed     (F-nat, F-IID, F-X+P, and S+F with --init)
      --arm server  (server pretraining on Feb 18 + 20)
      --arm cj      (central on clients + server events)
    S0 needs no training (evaluation of the server checkpoint).
  - --lr sets the peak learning rate (tuning grid, report 09 section 4).
  - Noise: the per-day pool v2 from step 2.
  - Guard: numpy.load refuses the pooled ssl_central bgpool.npy. Only the
    M5 selftest path (fold "m5", noise "m4") may switch the guard off, and
    the code asserts that.
  - Firewall per fold, in code: no training event may come from that fold's
    evaluation days, the tuning day or (except CJ) the server days. The
    server may not use any fold's evaluation days or the tuning day. The
    m4 "role" firewall was removed, as the protocol requires.
  - Monitoring: Feb 10 with Feb 10's own noise pool; no external reference
    model.
  - Provenance: each run records the sha256 of fedsim2, folds.json, the
    noise pool and the --init checkpoint.
  - Never overwrites: a run refuses to start if its output exists, and logs
    are opened in exclusive-create mode.
  - --plan-only builds the partition and the budget plan without training.

      events from a fold's evaluation day into a client raises: PASS.
  P   Partitions: each fold has 10 clients; IID sizes equal natural sizes;
      every event appears exactly once and IID covers the same events; every
      IID client mixes days.

        C0b client and global weights bit-identical under reversed client
            order: PASS
        C0c global = example-weighted mean of the clients: max |diff|

  S   Smoke run, 1 round of every arm on fold 0, monitoring on: all 9

  One FedAvg round about 1.9 s (200 rounds about 6.5 min). Central rounds

  GPU memory was released after the tests (110 MiB in use).

6. FINDINGS
  - No defects found. Every protocol requirement for step 3 is implemented
    and proven.
  - The F-X+P budget in fold 2 is 0.4 % above X+P, because 233 rounds
    round up there. Within the rounding tolerance stated in report 09
    section 3.2.

7. DEVIATIONS FROM PROTOCOL v2
  None in substance. Implementation choices not spelled out in report 09
  (they fix rounding only and are logged here):
    - rounds per arm: central arms R = 200, CJ R = 188 and server R = 184
      (chosen so that the budget divides exactly);
    - monitoring every 10 rounds by default.
