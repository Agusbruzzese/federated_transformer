# External audit: research/extraction/A_integrity

_20260929_213354 · served by claude-sonnet-5-5 · effort medium · 31956 in / 2794 out · ~$0.092_

## Verdict
ACCEPT WITH FIXES: the format and clock findings are largely well evidenced, but the report has an internal contradiction on the sampling rate, circular clock validation, an unsupported maximum-gap claim, and no pre-registered criteria. Some brief items are only partly answered.

## Issues
1. [MAJOR] REPORT F4 / mains_check.py: The mains check does not independently validate the 2416 Hz rate. It assumes the mains line is exactly 50.000 Hz, but grid frequency varies (typically ±0.1–0.2 Hz, i.e. ±0.4 % of fs would need ±0.2 Hz). The fs_mains scatter of ±3 Hz is about 0.12 %, the same order as the claimed drift. The finding "±0.2 % daily drift" and "diurnal ~1 %" cannot be separated from grid or PC-clock effects. Also, the wall-clock reference is filename timestamps quantised to 1 s, with an rms residual of 0.35 s and a maximum of 1.8 s. -> State the uncertainty budget. Downgrade "2416 Hz uniform grid" to "≈2416 ± few Hz, with the drift attributed to the PC clock or the ADC unresolved". The 60 chunks are also unstratified (random). Check the mains result against the 5-day mean.
2. [MAJOR] REPORT F4 vs bsd_io.py: The claim of a "uniform ADC grid" whose rate drifts ~1 % diurnally (device ticks) is contradictory unless the drifting clock is the device tick and not the ADC. Nothing establishes which clock drives the ADC. `FS_NOMINAL_EFFECTIVE=2415` is hard-coded as a global default in `load_chunk`, so time axes differ by up to 0.4 % from `fs_local` (range 2407–2421). -> Default to `fs_local` or document the error. Downstream filters and PSD frequencies (a 50 Hz notch) will be mistuned if they use 2400 or 2415 while the chunk-level rate is 2408–2421.
3. [MAJOR] REPORT F5 / scan_time_edges.py: n_missing_est is computed from only 2×2000 edge timestamps, and `base` is assumed constant across the 100k-sample chunk despite the claimed drift. The validation ("−22..+41 error, median 0") covers only a subset. The dropout rate per day (e.g. 1.7 %) is therefore an estimate from the edges only, with ±10-sample error per chunk. The mean ok-gap threshold of 1.5×median can also miss 1-sample losses, since dt for a 1-slot loss is ≈2×, but jitter is in play. The "1–5-sample losses" claim rests on full reads of only 484 chunks. -> Report the estimator bias as a function of drift, and validate on more chunks, particularly run 0204 late.
4. [MAJOR] REPORT F5: The maximum gap of 45.1 ms comes from 484 fully read chunks (≈0.3 % of ~29k) and is dominated by run 0204. Sampling covers only 384 random plus the 100 worst. "Largest gap 45.1 ms" and "at most 3 identical values" are sample-limited, yet the recommendation "No files need to be excluded" is asserted globally. -> Run a cheap full-Time-file gap scan (it is only 8 B/sample, but it is ≈ 11 GB, so use ≥1 process), or state the limitation explicitly.
5. [MAJOR] Slot reconstruction / bsd_io.slots_from_timestamps: Each sample after a gap is assumed to advance exactly one slot. An unflagged single-sample loss (dt < 1.5×median) is invisible, so the slot index silently drifts. Gap-size estimation uses the median of only 8 post-gap samples, and gaps closer than 8 samples fall back to `g2-g`, a possible w=… bug (bursts 12–40 apart are fine, but `w` can be tiny, e.g. 1). `est` with w=1 relies on the early first timestamp (0.3–0.7 slot early), so it is biased. `inc[g]=max(1,…)` also hides negative estimates. -> Quantify the error of the slot count against the wall-clock and mains checks for burst-heavy chunks.
6. [MAJOR] REPORT (all): The brief required hypotheses, pre-registered criteria and a confidence level per finding. There is no hypotheses or criteria section. Confidence levels such as "very high" are given for F8 and F1. -> Add the criteria, or state that they were not pre-registered.
7. [MINOR] list_chunks `_fit_wall_clock`: The clipping threshold `max(3σ, 1.0)` and the knot spacing were chosen post hoc. The fit is then tested by the self-test "|r|<2.5 s", which is circular (the fit is evaluated on its own training data). The 0.35 s rms residual mostly reflects filename quantisation. Flag the same in load_span's claim of "0.35 s absolute uncertainty".
8. [MINOR] Coverage (coverage_and_figures.py): the run-0224 truncation claim ("logger idled 2 h") is inferred from the folder name, and the day-24 hours_covered for 02-04 (8.60 h) is consistent. Coverage counts wall_end using `n_missing_est`, so the covered hours include dropouts. "Weekend data only Feb 8–9" is correct per table, but state that this severely limits C and D. Days 02-05 to 02-11 come from a single degraded run.
9. [MINOR] Value sanity (F7): the claim "no clipping, sentinels" is drawn from 484 chunks, and the "≈18 effective bits" and "σ≈62 counts" come from the second-difference MAD, which is biased by dropouts and the 50 Hz hum and is not a Welch measurement. "Low 4 bits uniform (χ²≈15)" is fine for 15 dof, but is reported without a p-value.
10. [MINOR] Reproducibility: the scripts hard-code an absolute path, the seeds are fixed (0, 1, 3), and the cache is committed. The self-test depends on hard-coded dates. `mains_check` and `sanity_scan` need `raw_header_scan.parquet` first, and there is no run-order README. The stdout of the sanity scan and the self-test is not saved, so "38/38" cannot be verified from the files.
11. [MINOR] load_span: `np.mean(fsl)` is unweighted. The forced monotone drop at chunk joins (`keep[i+1]=False`) silently deletes samples without reporting them in gaps.
12. [MINOR] Cross-workstream: the Time-not-µs finding conflicts with the brief's hypothesis. That is good, but other workstreams must be told to use `fs_local`, and the dropout-rate confound (run 0204) is listed only as a warning, not quantified for the federated splits.
