## Verdict
**ACCEPT WITH FIXES**: The pre-registered verdicts are reported honestly, and the report admits that P2a–c cannot be passed. But the headline CNN-vs-transformer conclusion, the "learns but leaks" label and the duration claim are weaker than stated, and several deviations lack the evidence needed to judge them.

## Issues

1. [MAJOR] REPORT.md verdict table: "Learns but leaks" for the transformer is not supported. The report's own D1 shows P2a–c fail because of the pooling, and within-space leakage is ≤0.021 (date) and ≤0.007 (run). The label is a mechanical output of a broken criterion. -> Report the pre-registered verdict as formally uninformative on leakage. State that the within-space result is the only valid leakage evidence, and that P2 was not validly tested.

2. [MAJOR] Within-space leakage probe (`evaluate.p2ws`): the probe is run on a space that includes each model's own training runs, with no nulls (n_perm=0). Date skill on training-run events measures memorisation, not leakage to held-out runs. No test of the held-out-run embeddings from a single model was done. -> Add a null for the within-space result. Run a probe restricted to the held-out run's dates, using only the single fold model that did not train on it.

3. [MAJOR] REPORT.md, P1: the P1 test compares SSL against a single-network random init, while the pooled OOF design costs −0.04 to −0.14 per target. The report admits this bias, yet still reports "CNN 0/4, No evidence of learning". D1 (SSL − fold-init) gives CNN 3/4 and TF 4/4, which contradicts that verdict. D1 was added after the freeze to the analysis plan, and its conclusions should be weighed accordingly. The CNN verdict is therefore an artefact of the evaluation design. -> Do not headline "No evidence of learning" for the CNN. Present both comparisons side by side, and give the matched fold-init comparison (D1) prominence.

4. [MAJOR] CNN preferred over the transformer: this follows the pre-registered rule (+0.015 [0.008, 0.022]), but the random-init baseline differs by 0.127. The pooled score is dominated by what a random CNN already encodes, and the tie-break on raw score is probably not meaningful. At SNR ≥ 30 the CI includes 0. -> Flag the CNN preference as low confidence. Give the gain-over-baseline comparison equal weight.

5. [MAJOR] Selection (`select.py`): margins ≤ 0.009 are noise-level, and selection used a seed-0 model only. Hyperparameters then differ per fold (for example the TF lr is 0.001 in folds 1 and 3 but 0.0003 in folds 0 and 2). Inter-fold hyperparameter heterogeneity is therefore noise. -> Report the sensitivity of the P1 results to the selected cell, or fix a single cell across folds.

6. [MAJOR] REPORT.md, duration claim: "duration hypothesis NOT supported" rests on the CNN no-stretch ablation, Δ −0.000. But the CNN loses log_dur versus random init (−0.053) and this is "unexplained". The kNN probe on a 64-d embedding with k=15 may saturate. A random-init CNN already scores 0.85 on log_dur, close to the best selection values. -> Mark the duration conclusion as inconclusive, not negative. Test with a ceiling or linear probe.

7. [MINOR] P2d and `p2_criteria`: the P2d null shows has_dropout skill ≈ 0.44 even for random-init at all-SNR, so the criterion is dominated by the blip population. The pass at SNR ≥ 20 is tested with a margin (+0.05) that was not calibrated against the permutation null. -> Report the margin relative to the null.

8. [MINOR] Deviations 1 and 6 (HGB date leakage not run, P5 not run): the missing HGB date leakage is not stated as a gap in the conclusions. HGB P2b–d ran with only 10 permutations. -> State explicitly that the non-linear leakage check is incomplete.

9. [MINOR] Reproducibility: training is not bit-reproducible (3 parallel GPU processes), and the report names no seed-variance bound on selection. Run order and shard assignments are fixed, but GPU non-determinism could change the selection outcome. -> Log whether the selection would survive a repeat of seed 0.

10. [MINOR] Orchestrator verification: it checks hashes and tables, not the code logic. `evaluate.fast_metric` for classes uses K = classes present in the OOF subset. Per-run subsets (`per_run`) may have a different K, so per-run deltas are on a different scale. -> Document this, or use a fixed K.

11. [MINOR] Sampling: run 0204 holds 1 800 of 4 375 events and carries the dropouts. Each fold's training population differs (2575 to 3693). Fold 0 trains on a different mix without the dropout run. -> Report fold-wise results alongside the pooled numbers in the headline.

12. [MINOR] The report says it "points to the tables" but the agent text is not preserved in the repo. Unverifiable claims include "J1–J17 written before training" (a config docstring is hashed, but not the full list). -> Archive the agent text.
