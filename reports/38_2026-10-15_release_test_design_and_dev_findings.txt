1. WHY
  M2 (TLS + authentication) and M3 (SecAgg+) were validated separately,
  on one machine, over loopback. The configuration that would be deployed
  (all of them together, sites in separate containers, real network links)
  had never run. This test runs exactly that.

2. SETUP
  - 11 containers on a private internal Docker network (image fl-base):
      flserver: SuperLink (TLS certificate, --enable-supernode-auth) and
        the ServerApp it spawns. It sees federation.json, the server
        folder, its own certificate and key, the CA certificate and the
        sites' PUBLIC keys. It has no site data, no site private keys and
        no CA key.
      site_00..site_09: one SuperNode each. Each sees only its own data
        folder, the CA certificate and its OWN key pair.
  - Site keys are registered by the operator (flwr supernode register)
    before the sites start.
  - Emulated WAN (tc netem):
      each site's uplink: 20 ms delay, 50 Mbit/s;
      server egress: 20 ms delay, 1 Gbit/s;
      so the round-trip time is at least 40 ms.
  - Traffic: each site container's network interface counters are read at
    every committed round. That interface IS the site-to-server link.
  - App: fl_system5/app = fl_system3 (M3, SecAgg+) with the guard of
    section 3. The client code is byte-identical to fl_system3.

3. DEVELOPMENT FINDINGS (before pre-registration)
  a. Configuration fixes: the container host name must match the
     certificate (flserver); the study environment (.venv) must be
     mounted read-only, because .venv-fl takes its numeric libraries from
     it.
  b. DEFECT FOUND IN M3's APP (fl_system3), invisible in all earlier runs
     because none had a failure:
       - A site container was killed during round 3 (rel_dev_kill).
       - Flower's SecAgg+ workflow logged "Not enough shares to recover
         secret in unmask vectors stage", did NOT call the strategy, and
         went on to round 4.
       - Round 4 then waited for the dead site indefinitely; only the
         launcher's stall watchdog (10 min) ended the run.
     Nothing wrong was committed (last committed round 2). But with a
     transient failure (a site that comes back), the run would have
     skipped round 3 and continued on a trajectory no test covers. This
     breaks the strict rule "no partial or skipped round".
     Fix (fl_system5/app): a round may only start if it directly follows
     the last committed round; otherwise the ServerApp stops with an
     error. Retested (rel_dev_kill2): the run stopped at round 4's start
     with "would follow committed round 2"; resumed with fresh containers;
     global weights r1, r2, r3, r5 and the final model are BIT-IDENTICAL
     to the exact simulator (dpsim, proven exact in report 37).
     fl_system3 itself is left unchanged as the M3 record. The guard
     belongs in any deployment.
  c. Traffic note: SecAgg+ sends masked values as 64-bit integers, so a
     site's upload is about 1.73 MB per round, twice the 0.86 MB float32
     model. Measured in dev: about 1.0 MB down and 1.9 MB up per site per
     round.
  d. Other dev runs: rel_dev2 (3 rounds, BIT-IDENTICAL to the simulator;
     about 40 s per round); rel_dev_intr2 (intruders refused).
     The dev run directories are kept as records.

4. PRE-REGISTERED CRITERIA (fl_system5/check_rel.py)
  R1 exactness: full S+F recipe, seed 0, 200 rounds, with the full stack
     and WAN emulation (rel_SpF_s0) vs the local SecAgg+ run m3c_SpF_s0.
     Global weights at rounds 1, 2, 3, 50, 100, 150, 200 and the final
     model must have max |diff| 0.0.
  R2 isolation (listed inside each container during R1):
       - site k sees only client_k, its own key pair and the CA
         certificate;
       - the server sees only federation.json and server/, the sites'
         public keys, its own certificate and key, and the CA certificate.
  R3 intruders (rel_intr): with only site_00 registered,
       - site_00 must be online;
       - plaintext with keys, foreign CA and unregistered key must exit
         non-zero;
       - a keyless plaintext node must never be online;
       - exactly 1 node may be online.
  R4 fault (rel_fault, 5-round schedule): site 3's container is killed
     during round 3.
       - The first attempt must stop unfinished, by the guard ("no
         skipped round").
       - Rounds must be committed in order with none missing.
       - A resume with fresh containers must finish.
       - Global r1, r2, r3, r5 and the final model must be BIT-IDENTICAL
         to the exact simulator (rel_ref5b_s0).
  R5 cost (reported, no pass/fail):
       - median MB down and up per site per round, and per run;
       - median round time vs the local M3c run (39.8 s).
