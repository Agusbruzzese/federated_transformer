SUMMARY
-------
The federated system now runs on Flower's current runtime:
  - a SuperLink (coordinator);
  - one SuperNode per site, each given only its own data folder;
  - a ServerApp driving strict FedAvg through the Grid message API;
  - a ClientApp per site.
It still computes exactly the study's models. The full 200-round deployment
recipe is BIT-IDENTICAL to the study's S+F model, even though the
SuperLink failed twice during the run and those rounds were replayed. All
M1 criteria pass.

1. HOW THE CURRENT RUNTIME DIFFERS, AND HOW IT WAS HANDLED (measured with
   probe apps)
  - A NEW ClientApp process is started for EVERY message. Flower 1.39's
    flwr-clientapp requires a one-time token per execution, in both
    isolation modes. Module state does not survive between rounds;
    Context.state does.
    -> All per-site state is restored every round from Context.state:
       AdamW moments, CUDA generator, batch-stream generator, permutation
       and position. A copy is also kept in the site's own folder for
       SuperNode restarts.
  - With no non-Flower dependencies declared, the ClientApp and ServerApp
    run in the SuperNode/SuperLink environment (.venv-fl): identical
    libraries, no downloads.
  - Site identity: the ServerApp queries every registered node, keeps only
    live ones, and maps exactly one per site (k = 0..9).

3. DEFECTS AND PLATFORM ISSUES FOUND (all fixed and re-tested)
  a. Flower app names must use hyphens (fl_system2 -> fl-system2).
  b. The launcher's child processes must get stdin from /dev/null (as
     shell background jobs do).
  c. Stale SuperNodes from earlier deployments survived SIGTERM and
     re-registered on the next SuperLink as dead nodes. The ServerApp then
     picked them and got "Node Unavailable" errors. Fixes: hard teardown
     (SIGTERM, then SIGKILL), a pre-flight check that refuses to start while
     Flower processes or ports are in use, and live-node mapping in the
     ServerApp.
  d. Platform issue (Flower SuperLink): under load from 10 sites, its SQLite
     state store raised "database is locked". In the first full run (m1b)
     one site's reply was lost in round 68 and the strict server stopped,
     correctly. Fixes:
       - a failed round is REPLAYED in full: every site restores its state
         of the previous round from its own disk, so the result is
         identical; a dead site still stops the run after max-retries = 2;
       - file-backed SuperLink database.
     In the second full run (m1b2) the problem recurred twice (rounds 130
     and 152: "reply message objects are unavailable"). Both rounds were
     replayed (about 4 min each), and the final model is STILL
     bit-identical. Retry exactness is thus proven under real failures, not
     only by design.

4. VERDICT
  M1 PASSES. The system no longer depends on the deprecated API, keeps every
  property validated before (exact computation, isolation, fault safety,
  exact recovery), and is robust to the transient platform failures seen in
  the current runtime.
